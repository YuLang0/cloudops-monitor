# 포트폴리오 소개글 — CloudOps Monitor

## 한 줄 소개

여러 서버의 자원 사용량을 실시간으로 수집·시각화하고, 기준 초과와 연결 끊김을 장애 이력으로 관리하는 서버 모니터링 웹서비스.

## 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 유형 | 개인 프로젝트 |
| 기술 | React · TypeScript · Tailwind CSS · Recharts / FastAPI · SQLAlchemy · SQLite / Python psutil / Docker Compose · nginx · Caddy |
| 구성 | 웹 대시보드, REST API 서버, 서버 설치형 Agent |
| 검증 | 백엔드 자동 테스트 128개(보안 점검 73개 포함), 프론트엔드 단위 테스트 17개 |

## 만든 이유

클라우드 엔지니어의 일은 "서버가 지금 괜찮은가"를 아는 데서 시작한다고 생각했습니다. 기존 도구를 설치해 보는 것만으로는 수집 → 저장 → 판단 → 표시가 어떻게 이어지는지 알기 어려워서, 작은 규모로 전 과정을 직접 구현했습니다.

## 주요 기능

- 서버 등록·수정·삭제, 서버별 CPU/RAM/디스크 경고·장애 기준 설정
- CPU, RAM, 디스크, 네트워크 송수신량, 가동 시간 수집 및 1분/5분/1시간/24시간 그래프
- 정상 / 경고 / 장애 / 연결 끊김 / 데이터 대기 상태 표시
- 장애 시작·해결 시각 기록, 심각도 분류, 중복 알림 방지
- 사용자별 서버 분리, 다크·라이트 모드, 모바일 화면, CSV 내보내기
- 실제 서버 없이 체험할 수 있는 데모 모드(가상 서버 4대)

## 설계에서 고민한 점

**1. "연결이 끊긴 서버를 정상으로 보여 주지 않는다"**
상태를 DB 에 저장해 두면 Agent 가 죽었을 때 마지막 상태인 "정상"이 계속 보입니다. 그래서 상태를 저장하지 않고, 조회할 때마다 마지막 수신 시각으로 계산하도록 했습니다. 30초 넘게 수신이 없으면 "연결 끊김"이 되고, 화면의 수치는 "마지막으로 받은 값"이라고 표시하며 전체 평균에서 제외합니다. 그래프도 끊긴 구간을 선으로 잇지 않습니다.

**2. Agent 가 보내는 구조(push)**
모니터링 서버가 각 서버에 접속해 값을 가져오는 방식은 대상 서버의 포트를 열어야 하고, 사용자가 입력한 주소로 서버가 요청을 보내게 되어 SSRF 위험이 생깁니다. Agent 가 밖으로 보내기만 하는 구조로 정해 두 문제를 함께 없앴습니다. Agent 에는 원격 명령 실행 기능을 넣지 않았습니다.

**3. 같은 장애로 알림이 반복되지 않게**
CPU 가 기준 근처에서 오르내리면 장애가 수십 건 생깁니다. "서버+항목당 진행 중 장애는 1건"을 DB 의 부분 유니크 인덱스로 보장하고, 기준 아래 값이 연속 3회 나와야 해결로 처리했습니다.

**4. 가상 데이터와 실제 데이터의 구분**
데모 서버는 별도 플래그로 저장되어 화면과 CSV 에 항상 "데모"로 표시됩니다. Agent 키가 발급되지 않아 실제 수집 경로로는 데이터를 넣을 수 없습니다. 반대로 가상 데이터도 저장·장애 감지는 실제와 같은 코드를 거치게 해서, 데모로 확인한 동작이 실제에서도 같도록 했습니다.

**5. 느린 응답에서도 멈추지 않는 갱신**
처음에는 3초마다 요청을 보내고 "가장 최근 요청의 응답만" 화면에 반영했습니다. 외부 점검에서 응답이 4초씩 걸리면 응답이 모두 버려져 화면이 멈추는 문제가 재현됐습니다. 요청을 한 번에 하나만 보내고 응답을 받은 뒤 다음 요청을 예약하도록 바꾸고, 수정 전 방식이 실패하는 상황 자체를 테스트로 남겼습니다.

**6. 무료 서버에 실제로 올릴 수 있는 운영 준비**
Oracle Cloud Always Free 기준으로 배포·업데이트·백업·복원 스크립트를 만들었습니다. 비밀키 자동 생성(출력 안 함), HTTPS 전에는 평문 접속을 막는 포트 구성, 백그라운드 작업의 중복 실행을 막는 파일 잠금, SQLite 온라인 백업과 '실행 중이면 복원 거부' 같은 안전장치를 넣고, Docker 가 없는 환경에서도 스크립트 흐름 전체를 대역을 써서 43개 항목으로 검증했습니다. 무엇을 실제로 검증했고 무엇이 서버에서만 확인 가능한지를 문서에 구분해 두었습니다.

## 보안

- 비밀번호 Argon2id 해싱, 로그인 실패 횟수 제한
- 세션 토큰을 HttpOnly·SameSite 쿠키로 전달
- 모든 조회에 소유자 검사(다른 사용자의 서버는 404)
- Agent 키는 해시만 저장하고 발급 시 한 번만 표시, 재발급 시 즉시 폐기
- 입력값 검증, CSV 수식 삽입 방지, CSP, 컨테이너 non-root 실행
- 비밀정보는 환경변수로만 관리

## 테스트

인증, 권한 분리, 입력 검증, 수집, 상태 계산, 장애 생성·중복 방지·해결, 시계열 집계, CSV, 데모 데이터를 pytest 128개로 검증했습니다. 이 중 73개는 다른 사용자의 서버 ID 를 직접 넣는 요청, Agent 키로 다른 서버에 쓰려는 요청, 비정상 측정값 같은 공격·오류 상황을 다루며, 이 과정에서 오류 응답이 입력값(비밀번호 포함)을 되돌려 주는 문제 등 4건을 찾아 고쳤습니다. 시간에 따라 결과가 달라지던 테스트 2개를 발견해 시각을 고정하는 방식으로 고쳤습니다. 실제 PC 에 Agent 를 실행해 측정값 반영, 연결 끊김 감지, 재시작 후 데이터 유지를 직접 확인했습니다.

## 한계와 다음 단계

- Docker 구성은 작성했지만 작성 시점에는 실행 환경이 없어 검증하지 못했습니다. → 클라우드 VM(예: AWS EC2)에 배포해 검증하고 과정을 기록
- 알림이 화면에만 표시됩니다. → 이메일/Slack 알림
- SQLite 단일 파일 저장입니다. → PostgreSQL 전환, 오래된 데이터 다운샘플링
- 백엔드 프로세스 1개 기준입니다. → 상태를 외부 저장소로 옮겨 수평 확장
- → GitHub Actions 로 테스트 자동화, Prometheus/Grafana 와 비교해 보기

## 배운 점

- 모니터링에서 가장 위험한 것은 "값이 나쁜 것"이 아니라 "값이 오지 않는데 괜찮아 보이는 것"이라는 점
- 보안은 기능을 추가하는 것보다 구조를 고르는 단계(push 방식, 키 저장 방식)에서 대부분 결정된다는 점
- 시간에 의존하는 코드는 테스트에서 시각을 직접 통제해야 한다는 점
